## 修正した動作

| 修正前の問題 | 修正後 | 確認方法 |
| --- | --- | --- |
| 保存先が欠落し一覧から消える | シナリオ・自動化・配信・リマインダ・自動応答・チャットを所属付きで保存 | 実SQL、作成・一覧API、ブラウザー保存と再読込 |
| 左上の選択とAPIの権限が違う | アカウント指定とスタッフ権限を検証。他アカウントのID、関連タグ・ステップ・フォームを拒否 | 所属外ID差し替えと権限テスト |
| 条件の未知キーが無条件一致になる | 対応するキー・型だけ保存。既存の不正条件も不一致 | 保存API、判定関数、画面での拒否表示 |
| 所属なしイベントから他アカウントの自動化が動く | 友だちの所属から対象を確定。自動化・スコア・通知・送信Webhookを同じLINEへ限定 | 実SQLとイベント処理、外部APIは架空応答 |
| 親停止後も個人登録が配信を続ける | 親と個人登録を停止。送信直前も状態確認。再有効化だけでは再開しない | 予約抽出・配信処理・停止中の遅延完了テスト |
| タグ・OR条件で配信先が横断する | 同じLINEのフォロー中の友だちだけ配信。送信前にLINE名と人数を表示 | 誤った旧タグ関係を含む配信・条件抽出テスト |
| 一括停止が全件対象／失敗しても完了 | 選択LINE内で一括更新し、残件を読んで完了判定 | DB失敗時の巻き戻し、ブラウザー停止、B変更なしの読み戻し |
| 不明な所属から既定トークンへ送信 | 所属不明・無効アカウントでは送信しない | 署名・送信処理・定期処理の対象外テスト |
| 同時実行や失敗後に再送する | シナリオの既存送信権確保を維持。リマインダへ送信権確保を追加。一斉配信は試行履歴で再送を抑制 | 同時リマインダ、タイムアウト、送信中停止テスト |
| 公開フォームで本人情報を偽れる | アカウント専用LoginチャネルでLINE ID tokenを検証。所属外・本人不一致は保存前に拒否 | 公開APIの未認証・別人・正常回答テスト |
| 今月の定義と表示が違う | 日本時間の当月1日から集計。課金集計や全LINE活動とは区別 | SQLレビューと操作ガイドの定義 |

## 検証の範囲

23項目の回帰テストに合格。Honoの実際のworkerを起動し、schemaとマイグレーションを適用したメモリ内SQLiteでSQLを実行します。外部通信は架空応答に置き換えます。実際のLINEサーバー、実機受信、本番D1はこの合格に含みません。

ブラウザーでは、APIキーログイン、表示対象と一覧の一致、シナリオ・自動化の停止状態での作成、再読込、未知条件の拒否、対象名付きの一括停止と完了表示を確認しました。停止後は架空Aの登録がpaused／次の予約なし、架空Bはactive／将来予約のままです。

## 本番適用の順序

1. ヒナタマ専用のworker・管理画面・DB・アカウントIDを確定する。共有workerと別workerの定期処理が重複しない配置を選ぶ。
2. 本番データを保全し、適用済みマイグレーションとテーブルの列を確認する。024〜026を、実スキーマに合わせて適用する。既に手動追加された列があれば同じALTERを重ねない。
3. 管理者以外のアカウント権限を `staff_line_accounts` へ明示的に付与する。024は空の表を作り、既存スタッフへ自動で全権限を渡さない。現時点では専用の権限付与GUIはない。
4. 対象専用のbackendとfrontendを一組として反映し、所属付き作成・停止・権限拒否を本番で読み戻す。旧フロントだけを新バックエンドへ接続しない。
5. 本人の診断→LINE追加→結果→相談→スタッフ確認→停止までテストする。スタッフの役割とアカウント権限も確認する。
6. 結果を確認してから、そのLINEのシナリオや応答だけを有効化する。

新アカウントのWebhook／LP切替は別工程です。修正の完了だけで接続済みとは扱いません。

## 残る制約

- 公式LINEの応答や過去トークを自動複製する機能は未実装。画像・設定の保全と移行仕様は別の保存作業です。
- 流入経路・UUID・オペレーター・広告設定・Stripe・トラフィックプールなどの旧全体管理機能は、専用workerで操作できません。広告CVの外部送信は、広告設定JSONの `line_account_id` が友だちの所属と一致するときだけ行います。既存の所属未指定設定は送信対象になりません。適用前に管理者が所属を確認し、意図した広告設定だけに明示します。
- 同じproviderの同一ユーザーIDを別OAへ追加するケースは、現在のfriends一意制約で拒否します。既存友だちの所属を書き換えて回避しません。複数OAへの同時所属には別のデータモデル移行が必要です。
- メッセージ受信の再配達や初回直接返信まで含む完全なexactly-onceは保証しません。送信済み・LINE API処理中の取り消しはできません。失敗・pendingの送信権は実績を確認して復旧します。
- APIにはあってもGUIにない機能が残ります。JSON編集や一部の個人登録操作を店舗スタッフが簡単に扱える状態まで作り込んだものではありません。
- 汎用OAuthのstate保護、全体管理データの完全な所属分離、旧データ修復は別課題です。この修正をシステム全体のセキュリティ保証として扱いません。

復旧時はworker・UIの一組を戻し、DBは追加列を保ったまま扱います。旧版へ戻すと今回の誤作動経路も戻るため、そのまま自動配信を再開せず対象を限定して確認します。
